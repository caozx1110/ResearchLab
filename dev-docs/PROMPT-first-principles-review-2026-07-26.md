4. 记录我随手产生的想法

## 二、review 方法（第一性原理，独立作业）

1. **先不要读** `dev-docs/reviews/` 下任何既有审阅、蓝图、施工报告——先形成你自己的判断，最后一步才去 diff。
2. **从需求倒推理想形态**：对上面每一条需求，先独立写下"理想情况下这件事应该几步完成、我需要说几句话、大概消耗多少 token"；然后实测当前系统的真实路径，记录差距。
3. **实测，不是读代码**：安装到 /tmp 的 scratch 工作区实际跑（`bash install.sh --claude --project /tmp/ws-review`）。你在我本机、有网络：**真实 arXiv 论文、真实 PDF、真实 GitHub repo 都要走一遍**（这是此前云端 review 做不到的部分，价值最高）。仓库根的 `kb/` 是我的真实研究数据：只读，严禁写入或删除。
4. 每条需求输出四个量：理想步数 vs 实际步数（含对话轮次）、摩擦点、token 消耗判断（哪里在重复读/重复生成）、结果可信度（产出能不能不核对原文就用）。
5. 专门做两个清单：**过度工程**（哪些机制对单人研究者是负资产——每保留一道门就多一次打断，指名道姓该删什么/降档什么）与**缺失能力**（需求有、系统无或名存实亡）。
6. 角色扮演压力测试：挑 3 个场景完整模拟真实使用（例如"入库一篇今天的 arXiv 论文并讨论它是否值得跟进""基于库里材料陪我打磨一个 idea""周五下午 10 分钟出本周周报"），把对话轮次和卡点如实记录。
7. **最后**读 `dev-docs/reviews/` 的既有审阅与蓝图（v2 为准），列出：你不同意的结论、他们遗漏你发现的点、你验证后推翻或加强的判断。

## 三、输出

写入 `dev-docs/reviews/first-principles-review-<今日日期>.md`：
1. 需求 × 路径实测矩阵（14 条逐条：理想/实际/摩擦/可信度）
2. Top 10 问题，按对我真实工作流的影响排序，每条带实测证据（命令与输出摘录）
3. 过度工程清单（删/降档建议）与缺失能力清单
4. 一天内能完成的 quick wins（≤5 个）
5. 与既有蓝图的分歧点（明确写"同意/反对/补充"）
6. 一句话总判断：这套系统现在值不值得我每天用；如果不值，通往"值得"的最短路径是什么
