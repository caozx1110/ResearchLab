## 0. 一句话结论

造出来的是一个优秀的「科研资料归档协议 + CLI 骨架」，但它还不是需求里要的「科研 AI 系统」——因为第一性原理里藏着三个未经检验的假设，而系统正在这三个假设上**静默失败**。

骨架（文件协议、confirmation 词汇、program spine、治理红线）是真的好，可以继续演化。但离想要的样子，不是「再补几个 skill」的距离，而是「价值重心放错了地方」的距离。

## 1. 已经做对的（不铺张，三条）

1. **把资产从聊天拉回文件**：`kb/units | programs | synthesis | config` 分层是对的，是所有长期价值的地基。
2. **信息类型 + confirmation 词汇**：`fact/inference/evaluation/user_opinion/unverified` × `pending/confirmed` 是极重要的信任语言，很多同类系统根本没有。
3. **自我审查纪律惊人**：已做 8 轮对抗审查、治理红线（禁自签、必留 evidence）守得很死。这个「元能力」比大多数 skill 本身更值钱。

## 2. 核心：第一性原理里三个正在失败的假设

总纲是——**「把能自动化的都自动化，人类只做讨论和确认」**。这句话里有三个隐藏假设，每一个都能用当前数据证伪。

### 假设 1：「AI 产出足够可信，所以'确认'是廉价动作」→ 被数据击穿

当前 KB 实测：**82 个 unit record，314 处 `pending_user_confirmation`，`confirmed` = 0**。人面向首页 `kb/user/current-state.md` 的「Confirmed Highlights」写着**「暂无已确认条目」**。

这不是小瑕疵，是**整个信任模型从未成功运转过一次**的铁证。为什么 0 确认？三个可能原因都指向同一个设计缺陷：

- **要么** 确认一条浅层 AI 判断的成本 ≈ 自己重做（得把它的推理链重建一遍才能判断对错）——那自动化没省人力，只是把负担从「做」挪到「审」，而审烂稿比自己写更累；
- **要么** 内容太浅，不值得确认；
- **要么** 一周堆 18+ 条、每条要 exact-id + confirmed-by + evidence，人跟不上（Part C 已诊断「手动操作太多」，但当成 UX 摩擦修，没看到**这是信任模型的经济学问题**）。

**遗漏点**：把「确认」设计成了**二元的、永久的、逐条的**闸门。但信任在现实中是**渐进的、按轨道分的、可累积的**。系统没有任何「这个 AI 在 paper 元数据上已经对了 50 次，以后这类不用审」的机制。结果 314 条 pending 变成**信任坟场**，而不是阀门。

> **实证（2026-07-09，当前版本）**：确认门比「太重」更糟——它是**空心的**。测试里把一篇 `core_content` **8 个字段全为 EMPTY**（research_problem/motivation/method/innovations/mechanism… 全空）的 note，轻松 promote 成 `confirmation_status: confirmed / maturity: complete / information_types: ['fact']`，provenance 的 evidence 指向那篇空 note 自己（`record.yaml` 实测）。**门只校验「有没有人名 + 有没有 evidence 字符串」，不校验内容是否非空、是否真实**。也就是说：不仅「确认廉价」是错觉（真去审是贵的），连「已确认」这个状态本身都不保证内容存在。信任模型是**程序性图章，不是实质保证**。

### 假设 2：「科研的瓶颈是整理归档，所以自动化那个」→ 价值重心放反了

17 个 skill 的分布：
- **输入/整理侧（约 10 个）**：source-intake、paper/repo/blog-analyst、literature-synthesizer、kb-manager、config-manager、navigator、wiki-adapter、discussion-archivist。
- **产出侧（4 个）**：idea-workbench、method-designer、experiment-workbench、report-author。

而需求文档里列的**最高价值需求**是产出侧：「落实 idea、展开方法构思、整理实验结果、构思论文大纲、撰写周报」。偏偏这 4 个最薄——实现层审查已证：method = 通用矩阵、experiment = 记录器不是验证器、report = 事件流 dump。

**力气花在了科研里最不值钱的一半（归档），在最值钱的一半（产出）上最弱。** 归档做到 100 分，只是让人更快找到资料；真正的价值是资料变成方法、实验、论文。这不是 bug，是**战略性错配**。

> **实证（2026-07-09，当前版本）**：连「归档侧」也分两层——脚本能做的（真实产物）vs 只能靠 agent 手写的（模板占位）。当前版本入库 AR-FB 一篇的实测：
> - **脚本真能产出的**：14 张裁剪好的 figure PNG + 真实 caption、parse-cache 的 16 段原文、`keyword_hits`、从文件名抠的 arxiv_id。这些是真价值。
> - **纯模板/启发式（换任何论文都长一样）**：`novelty/experiment/reliability` 的评级 = **硬编码关键词命中数**（实测 `keyword_hits.novelty: ['first','introduce']` → 因为出现了这两个词就评 strong，不是理解）；`risks`/`takeaways` 是**固定常量字符串**；`note.md` 约 10 节里**只有 1 节有真内容**，而且那节是**PDF 首页字节的原样粘贴**（含换行错乱），其余全是「方法机制：」「可引用表述：」这种空占位。
> - **冒烟枪**：`record.yaml.payload.core_content` 的 8 个理解型字段**全空**。
> 
> 也就是说：**脚本负责搬运和裁图（真活），"理解"这一层是留白给 agent 手写的**——`note_template()` 明确产的是「给 AI 填的提示」。审查里「analyzer 停在模板级」不是推测，是当前版本的设计事实。而且 `screen` 步骤自带一句 fallback 警告「未配置 LLM screening backend，回退到 heuristic」——**关键词启发式是"真 LLM 筛选"的明示降级替身**，作者自己知道这是占位。

### 假设 3：「知识库是累积的静态资产」→ 但科研领域是活的

系统把 KB 当档案柜：只进不出、只增不减、只存不校。但一个研究方向是**移动靶**：
- SOTA 每周在变，存的「趋势」下个月就旧；
- 识别的「gap」可能已被别人填了；
- 新论文可能**直接反驳** KB 里某条已存信念——系统无机制发现这种矛盾；
- confirmed 的判断永远不再复查。

需求里的「理清发展脉络和趋势」「讨论 idea 有理有据」，本质都要求 KB 是**活的、有时间维度的、会自我修正的**。当前结构上做不到——`literature-synthesizer` 只是数 tag 直方图，没有任何「领域动态」概念。

## 3. 需求本身遗漏的关键点（直接回答「我是否漏掉了什么」）

以下每条都是**需求文档里就缺的**，不是实现没跟上，是根本没想到。

**G1 — 需求点名「构思论文大纲」，但系统里没有任何 owner。**
grep 全部 SKILL.md：`outline / 论文大纲 / manuscript / paper-writing` **零命中**。report-author 只有 `weekly / ppt-materials / stage-summary / writing-materials`（`report.py:32`）。「从 KB 拉相关工作 → 排章节 → 规划图表 → draft 各 section」这条明确点名的流，**没有骨架、没有 owner**。字面意义的缺失。

**G2 — 「讨论」是给自己保留的核心角色，但系统只'归档'讨论，不'主持'讨论。**
discussion-archivist 只有 **1 个动词 `archive`**（`archive.py`）——事后记录。没有任何 skill 会**当对手**：苏格拉底式追问、基于 KB 唱反调、主动甩反例、追踪论证链。需求说要 AI「有理有据地讨论 idea」，系统给的是**录音笔，不是陪练**。第一等能力却连接口都没有。

**G3 — 「辅助论文阅读」被自己等同于「入库」，但它是独立模式。**
当前全是**批处理**：intake → note → confirm。没有**交互式伴读**：「这段在讲什么/为什么重要/和读过的 X 什么关系」。grep `explain/companion/reading-assist` = 0 命中。读一篇论文当下想问的问题，和事后归档它，是两种交互，被混成了一个。

**G4 — 需求里完全没有「时间维度」。** 两个都缺：
- **发现/监测（push）**：系统 100% 拉动式（喂论文才动）。没有「这周 arxiv 上该看什么」。列了「检索」，没列「监测」——而「发掘 idea」很大程度依赖对**新出现**东西的感知，不只是对已存东西的重组。
- **衰减/自校正**：假设 3 说的。没有 stale 标记、没有矛盾检测、没有复查周期。

**G5 — 问「距离想要的样子还有多远」，但从没定义「想要的样子」长什么样。**
系统没有任何**研究价值的验收标尺**。没有一组黄金问题（「给领域出 20 个问题，系统能否有据地答」）。**没有尺子，永远不知道有多远，也不知道每次改动是进步还是自嗨。** 这本身就是最该补的东西。

**G6 — 把「节省 token」当目标，却把「人的注意力」当免费。**
稀缺资源不是 token（机器成本），是**注意力**。系统疯狂产出 artifact（note、event、card、page），每个都是可能要读/审/维护的东西。314 条 pending 就是**注意力债务**，首页「暂无已确认」正是症状。一个「把能自动化都自动化」的系统，如果没有**冷酷的「现在只有这 3 件事值得看」过滤器**，只会把人埋了。

**G7 — 「不可变原始源 / 可深度追溯」对 PDF 是假象。**
`core.py:2295 backup_source` 只对 HTML 文本快照；arxiv/PDF 走 non-HTML 分支 → `file_hash=""`，只打 warning，**什么都没存**（`core.py:2303-2325`）。而 `raw/` 被 gitignore。科研主力源（arxiv PDF）**根本没被归档**，link rot 后不可恢复。要的「可追溯到页码/段落」这个证据层的**地基，对最重要的源类型是空的**。（BACKLOG B10 标了，但被 HOLD 成「只报警不下载」——等于承认地基是空的。）

**G8 — 没区分「选择推进」和「确认为事实」。**
两件事都塞进同一个 confirmation gate，导致人要么被迫为「我想试试这个 idea」这种轻决策走重确认，要么绕过闸门。信任的粒度错了。（OPTIMIZATION_PLAN S1/A4 已部分触及 idea select 的解耦，但没上升为通用原则。）

## 4. 成熟度定位（不是打分，是坐标）

用需求的能力谱标：

| 能力 | 要的 | 现状 | 差距性质 |
|---|---|---|---|
| 材料归档/检索 | 统一入库、可检索 | **骨架成立**，检索是词级 substring（`retrieval.py`） | 优化，非重造 |
| 提取核心概念 | 读懂、抽概念 | **模板+关键词计数**（`paper.py:258-262` 用命中数评「结果强度」；`blog.py` 107 行占位符，literal `待确认`） | **能力缺失** |
| 快速回顾要点 | 不重读原文 | note scaffold 存在，内容未被验证是否真提取 | 半成品 |
| 理清脉络/趋势 | 结构化领域理解 | 数 tag 直方图 | **能力缺失** |
| 讨论 idea（有据） | AI 当陪练 | 只归档，不主持 | **模式缺失** |
| 落实 idea → 方法 | 可执行方法 | 通用矩阵 | 薄 |
| 整理实验 | 验证+诊断 | 记录器，不验证 | 薄 |
| 构思论文大纲 | 排章节+拉相关工作 | **无 owner** | **完全缺失** |
| 周报/汇报 | 平时积累自动汇总 | 事件流 dump | 薄 |
| 自动化+人只确认 | 人只讨论/拍板 | **0/314 确认，闸门从未运转** | **模型失败** |

**定位**：输入侧归档是 **60-70 分可用骨架**；输出侧产出和「活的领域理解」是 **15-25 分占位符**；作为核心卖点的「人只确认」闭环，**实测运转率为 0**。

粗略说：**归档层再走一步就能日用；但真正想要的那个「科研合作者」现在完成度约两成，缺的不是工作量，是几个还没被设计的模式（伴读、陪练、大纲、监测、自校正）。**

## 5. 三件最高杠杆的事（与现有 roadmap 不同）

现有 roadmap（BACKLOG）当前重心是**重构+打包+发布**（god-file 拆分、install.sh、OSS readiness）——工程卫生，不是科研价值。建议把顺序换成：

### 高杠杆 1：立一把尺子（G5）—— 先做「研究价值验收集」
针对两个真实 program 各写 15-20 个**本来就会问**的问题（「physics-aware FB 的 z-space 和 PULSE 的 latent 关键区别？」「HITTER 的 whole-body control 用了什么 reward？」），让系统现在就答一遍。几乎零工程，却第一次给出「多远」的坐标，也暴露真实短板。**没有尺子，后面全是盲改。**

### 高杠杆 2：analyzer 从「Python 填模板」改成「LLM 产出 + 脚本验证证据」（假设 1+2 的解药）
关键认知：**Python 脚本永远抽不出「理解」——理解只能来自 agent。** 别再写更聪明的 Python extractor；要做的是**定义 agent 必须交付的结构（带 evidence 指针），再用脚本验证每条判断能追到页码/段落/文件行**。confirmation 从「审整条 record」变成「抽查证据在不在」——这才让「确认」重新变廉价，救活 0/314。这是把系统从「资料管理器」变成「研究助手」的唯一支点。

### 高杠杆 3：补两个缺失的模式，而非补 skill 数量：伴读（G3）+ 陪练（G2）
这两个是**明确要、系统完全没有**的高价值交互，且不需要重型工程——需要的是「给 agent 一个把 KB 证据拉进当下对话」的入口（实现层审查的 evidence-pack 正是这个的雏形，只是没人点破它其实是「讨论/伴读模式」的引擎）。

> 顺带把 G7（PDF 真下载）修了——否则高杠杆 2 的证据层没源可追，是空中楼阁。

## 6. 与实现层审查（ADVERSARIAL_SKILL_AUDIT）的关系

两份审查在**做什么**上高度一致，但**为什么**不同：
- 实现层审查说「analyzer 停在模板级」→ 本份说「因为假设了 Python 能抽理解，而理解只能来自 agent」。
- 实现层审查说「证据没绑定到 claim 级」→ 本份说「因为把确认当廉价二元动作，没意识到证据抽查才是让确认廉价的唯一路径」。
- 实现层审查开了 evidence-pack schema → 本份说「evidence-pack 的真正身份是讨论/伴读模式的引擎，不只是检索增强」。

**共识优先级**（两份都指向）：证据层做实 > 检索升级 > analyzer 变 extractor > spine 闭环。
**本份新增**：先立验收尺子（G5）、补论文大纲 owner（G1）、补陪练/伴读模式（G2/G3）、注意力预算过滤器（G6）、PDF 真归档（G7）。

## 7. 待用户拍板的方向

审查已完成。若要落地，三个最有杠杆的候选：
