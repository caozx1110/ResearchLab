# Markdown-first 产品愿景

> [!warning] Proposal 边界
> 本文描述的是目标人类层。当前 accepted/main 与 development 候选仍以现有 record、source bundle、evidence 和 managed projection 合同为准；“Markdown 是语义真相”只有在后续 ADR/Issue/PR 接受后才生效。

## 要解决的问题

研究工作通常跨越数周或数月：论文、代码、实验、讨论和决定散落在不同会话里。真正的失败不是“找不到一篇资料”，而是重新打开工作区时无法回答：

- 当前问题和范围是什么？
- 哪些话是材料原文，哪些是 Agent 的解释？
- 哪些判断已经被人接受，哪些仍需复核？
- 为什么做了这个选择？下一步如何验证？

系统的长期价值是让研究上下文可以复开、追溯、修改和恢复。

## 产品承诺

系统不承诺 AI 永远正确，只承诺：

1. 重要判断能回到来源中的逐字证据；
2. 人类可以直接阅读和编辑长期知识；
3. 材料或判断变化后，旧结论不会继续伪装成当前结论；
4. 中断和失败不会留下半成品或静默覆盖人工内容；
5. Markdown 正文可以脱离本系统在 Obsidian、Git 和普通编辑器中阅读；双链、查询和增强视图在不支持的工具中诚实降级。

## 用户看到的五条能力链

1. **收集**：保存论文、代码仓、网页、实验结果和人工笔记。
2. **理解**：从材料中提炼带证据的 Claim 和仍待回答的 Question。
3. **审查**：人确认、拒绝或暂缓高价值判断。
4. **行动**：围绕项目做 Decision、Experiment 或其他可验证行动。
5. **回顾**：形成综述、周报、报告和可重建导航。

Skill 是实现这些链的内部能力，不是用户必须学习的分类。

## 目标用户与非目标

首要用户是独立研究者或小型研究组：需要把材料、理解和实验连续维护数月，并愿意用 Git/Markdown 保留自己的数据。

当前非目标：

- 替人自动做最终科学结论；
- 把系统做成无边界的通用 wiki；
- 强制安装 Obsidian 插件、后台 daemon 或商业检索服务；
- 在尚未解决单人体验前承诺复杂的多人权限和云端协作。

## 设计原则

- **人类拥有语义正文**：Markdown 页面可编辑；系统只维护明确的来源、证据和完整性边界。
- **证据先于断言**：Claim 有逐字引用和稳定定位；冲突证据并列保留。
- **状态与认识分离**：工作流状态（草稿、待审、已采用、需复核）不冒充真理分数。
- **自动化有边界**：确定、可逆的机械动作自动；改变认识、行动或外部世界的动作停在不同的人类闸口。
- **视图可重建**：`Views/**`、全局索引、Bases 和报告是导航/输出，不成为唯一真相；`Home.md` 的人类正文保留原样，只更新显式 managed 区块。
- **来源可回退**：Markdown 阅读层损坏或不完整时，仍可回到原始 HTML、PDF 或原文件。

## 成功指标

- 新会话只看 `Home.md` 和相关页面，就能复述问题、证据、决定和下一步；
- 重要 Claim 两跳内可回到原文；
- 待审项目少而有价值，不把内部协议变成人类审批负担；
- 人工编辑后能看见哪些判断需要复核；
- 任意失败都能说明停在哪里、可继续什么或如何回到上一个完整状态；
- 同一 Claim 能被多个项目、报告或实验复用。

## 建议分期

- **V1**：根 `Home.md`、Source bundle、Notes、统一 Review Inbox，证明“可读、可复开、可追溯”。
- **V2**：Projects、Decisions、Experiments 闭环，证明知识能推动行动。
- **V3**：跨项目综合、可选语义导航、监控和发布视图；仍不把派生索引当真相。
