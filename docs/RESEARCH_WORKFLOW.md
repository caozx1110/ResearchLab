# 用科研工作流：你要做什么，系统替你做什么

> 这份文档从**用户视角**出发：你（研究者）到底需要动手做什么，哪些是系统自动完成的，以及怎么用它把科研从"论文→想法→方法→实验→产出"完整跑起来。
> 先记住一句话：**你负责"判断和拍板"，系统负责"记录、整理、检索、生成"。**

---

## 0. 你 vs 系统：分工

| 只有你能做（需要人） | 系统自动做（不用你操心） |
|---|---|
| 提供**原始材料**（论文链接、仓库、想法一句话） | 去重、备份原件、建结构化 record |
| **确认** AI 的判断（值不值得读、novelty、失败诊断） | 抽 PDF、生成笔记/图表、打标签、建索引 |
| 做**方向性决策**（选哪个 idea、选哪个 baseline、下一阶段做什么） | 记录决策、维护 program 状态、自动 git 存档 |
| 提供**实验反馈**（跑完的指标、观察） | 汇总成周报/PPT 素材、追踪待解问题 |

> 核心设计：**AI 说的话默认"待你确认"**。系统不会把 AI 的推断当成既定事实——这是为了让你的科研结论始终可信、可追溯。

---

## 1. 怎么用它做科研（最省力的方式）

**你不需要背命令。** 推荐做法是**用中文对 AI 说人话**，AI 会调用底层 skill 帮你落成文件。下面每个场景都给"你说的话"，需要时再给对应命令。

### 万能起手式（不知道先做什么时）

> 「请读取当前 v2 knowledge base，判断我现在最该做哪一步，并直接执行。」

系统会看你的 program 状态、待解问题、待确认项，给出并执行下一步。（底层：`orchestrate.py next`）

---

## 2. 场景 A：扩充知识库（加论文 / 仓库 / 博客）

**你做的**：丢给它一个链接或路径，说一句话。

> 「请把这篇论文先轻量入库，再判断是否值得细读：<arxiv 链接>」

**系统做的**（自动串起来）：
1. **入库**：去重 → 备份原件到 `kb/raw/` → 建 `record.yaml`（`source-intake`）
2. **快速筛选**：抽 PDF 前几页+摘要，给"值不值得读"的判断（`paper-analyst screen`）
3. 判断标 `pending`——**等你点头**

**轮到你**：看它的筛选结论，说「值得，做完整笔记」或「不值得，defer」。值得的话：

> 「做完整笔记 + 抽图表，然后我确认。」

系统写完整笔记 / 抽图 → 你**确认**（这一步只有你能做）：

> 「我确认这篇，确认人 czx，依据就是这份笔记。」
> 底层：`paper.py confirm --paper-id <id> --confirmed-by czx --evidence <笔记路径>`

**仓库 / 博客同理**：说「把这个 repo 变成知识单元，给能力边界和复用价值」/「总结这篇博客并判断可信度」。

> 💡 扩充知识库 = 你只提供**来源** + 做**该不该细读/确认**的判断；其余系统包办。

---

## 3. 场景 B：迭代 idea（从模糊想法到可验证问题）

**你做的**：给一句话想法，或让它基于知识库生成候选。

> 「把这个想法做成可评审的 idea，并分析 novelty / 可行性 / 最小验证路径：<你的想法>」
> 或：「基于当前已入库论文，给我 3 个候选 idea。」

**系统做的**：
- `idea capture` / `generate`：建 idea 卡片（可多候选）
- `idea analyze` / `review`：novelty、feasibility、最小验证路径分析（标 `pending`）

**轮到你**：这是**方向性决策**，只有你能拍板：

> 「选第 2 个候选推进，确认人 czx，依据是这段决策记录。」
> 底层：`idea.py select --idea-id <id> --confirmed-by czx --evidence <decision-log>`

**迭代**：不满意就说「再改 hypothesis / 换个角度重生成」——idea 的历史会保留，不会被覆盖。

> 💡 迭代 idea = 系统帮你**扩散+分析**，你负责**收敛+选定**。

---

## 4. 场景 C：迭代方法与实验（把 idea 跑成结果）

### C1 方法设计
> 「把选定的 idea 变成方法设计，挂到 program `my-program` 上。」
> 底层：`method.py design --idea-id <id> --program-id my-program`

系统选 repo、定接口、展开**实验矩阵**（默认+备选臂）。

### C2 实验循环（每一轮）
| 你说 | 系统做 |
|---|---|
| 「为这个假设建实验计划」 | `experiment plan`：建实验 record + 挂 program |
| 「记录这次 run：改了 X，结果指标 Y」 | `experiment log-run`：只记**事实**到 run-log |
| 「分析为什么没达标」 | `experiment diagnose`：AI 推断存 diagnoses（**待你确认**） |
| 「这轮结论我确认」 | `experiment confirm`（带确认人+依据） |

**轮到你**：跑实验、把**真实指标/观察**喂回来、确认诊断、决定「继续 / 改方案 / 换臂 / 停」。

### C3 阶段推进
> 「这个阶段的反馈我给你了，更新 program 状态并给下一步建议。」

系统更新 `state.yaml`、追加决策日志、把新问题登记成 open-questions、必要时进周报事件流。

> 💡 迭代方法实验 = 你提供**真实实验反馈+方向决策**，系统维护**状态+历史+待办**。

---

## 5. 场景 D：形成完整科研产出

- **综述/趋势/方法分类**：「基于已入库单元，给这个方向做综述和方法分类。」（`synthesize survey/taxonomy`）
- **周报/PPT/写作素材**：「为 `my-program` 生成周报和 PPT 素材。」（`report weekly/ppt-materials`）——它从**事件流**自动汇总，你过程里做的每步都已沉淀。
- **看全局/重开**：「刷新我的入口页，告诉我现在该看什么。」（`navigate refresh` + 本地浏览器 Workbench）
- **清确认账**：「列出所有待我确认的东西。」（`kb review-queue`）

---

## 6. "只有你能做"的四件事（其余都可托付）

1. **给来源**：链接、仓库、想法、实验数据。
2. **做确认**：AI 的推断/评价/诊断，点头才算数（且要留确认人+依据）。
3. **做决策**：选 idea、选 baseline、定下一阶段、停/继续。
4. **给实验反馈**：真实跑出来的指标和观察。

其余（去重、备份、笔记、图表、标签、索引、状态、历史、报告）都是系统的活。

---

## 7. 建议的节奏

- **随手**：遇到值得存的论文/仓库/想法，一句话丢进去（场景 A/B）。
- **每天**：起手式问「我现在最该做哪一步」；顺手清一下 `review-queue` 待确认项。
- **每周**：让它出周报；看 program dashboard 有没有阻塞的证据/问题。
- **每阶段**：喂实验反馈 → 让它更新状态 + 给下一步建议 → 你拍板。
